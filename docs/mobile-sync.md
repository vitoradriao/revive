# Sincronização durável das mutações mobile

As operações `record.create`, `relapse.create`, `goal.create` e `goal.complete` entram na fila SQLite por usuário antes da primeira chamada de rede. A linha conserva UUID de idempotência, tipo, payload versionado, instante real do evento e ordem de inserção local. A fila segue a ordem de inserção, mesmo quando uma recaída relata um evento ocorrido antes de outras alterações. Se o processo fechar antes do envio, a próxima inicialização retoma a mesma linha e a mesma chave.

No servidor, `execute_mobile_mutation` grava o recibo, executa a alteração de domínio e armazena status/resposta dentro de uma função PostgreSQL. Uma falha antes do commit reverte os três passos. Duas chamadas concorrentes com a mesma conta e chave esperam a transação proprietária; chamadas seguintes devolvem o mesmo status e corpo. Conteúdo diferente para uma chave retorna `IDEMPOTENCY_CONFLITO`. Recibos antigos sem corpo continuam retornando `IDEMPOTENCY_EM_PROCESSAMENTO`, que pode ser tentado novamente.

O hash novo ordena recursivamente as propriedades JSON. Para compatibilidade com recibos emitidos por versões anteriores, o servidor também verifica o hash JSON legado. O campo `expires_at` é mantido por compatibilidade de esquema, mas recibos novos recebem `infinity`; nenhum job de limpeza deve removê-los enquanto filas antigas puderem ser reabertas. A exclusão da conta apaga recibos e filas sob a cascata existente. Se um banco administrado externamente aplicar retenção manual, uma operação sem recibo deve ser resolvida por suporte antes de reenviá-la; a API não promete deduplicação ilimitada depois da exclusão do recibo.

Após enviar o lote consecutivo aceito, o app busca um único snapshot canônico e, numa transação SQLite, grava esse snapshot e remove todas as operações confirmadas do lote. Assim, o UUID local temporário é substituído pelo ID do servidor sem uma leitura completa por evento. Se o processo parar ou o snapshot falhar depois do commit remoto, a fila permanece; o replay usa as mesmas chaves e recupera as respostas originais antes de reconciliar novamente.

Falhas de rede, timeout, HTTP 408/429/5xx e conflito legado em processamento respeitam backoff e bloqueiam eventos posteriores para manter a ordem. Erros de validação/autorização e conflito de conteúdo ficam visíveis na tela **Sincronização** para correção ou descarte explícito. Filas legadas permanecem na tabela versionada existente; a instalação não apaga operações como parte desta mudança. Eventos incompatíveis continuam preservados para recuperação manual.

Os testes em PostgreSQL real cobrem chamadas simultâneas, hash independente da ordem das propriedades, conflito de conteúdo, falha injetada após a reserva e recuperação com a mesma chave. Eles não substituem os testes em aparelho físico de encerramento do processo, que pertencem à homologação Android da issue #7.
